# Finite Triage

Adapted from Matt Pocock's [triage](https://github.com/mattpocock/skills/tree/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/triage).
See [LICENSE](../LICENSE).

Read [issue-tracker.md](../../../docs/agents/issue-tracker.md),
[triage-labels.md](../../../docs/agents/triage-labels.md), and
[domain.md](../../../docs/agents/domain.md). Use the category and role mappings
there. Review GitHub PRs as implementation artifacts; this queue contains
Linear requests. Apply relevant AGENTS.md constraints.

Every issue or comment posted during triage starts with:

> *This was generated by AI during triage.*

## Roles and transitions

Categories are `bug` and `enhancement`. Roles are `needs-triage`, `needs-info`,
`ready-for-agent`, `ready-for-human`, and `wontfix`. Use the configured Linear
representation, including Canceled for `wontfix`. Each active triaged request
has one category and one role. Flag conflicting roles for the maintainer.

A request without a triage role normally enters `needs-triage`, then moves to
one of the other roles. A `needs-info` request returns to `needs-triage` when
the reporter supplies the requested information. The maintainer can override
the route; explain unusual transitions and ask before proceeding. Required
spec approval remains a separate gate.

## Show what needs attention

For a queue request, list these buckets oldest first, with counts and a short
summary per issue:

1. Open requests lacking a triage classification, even if they have area labels.
2. Requests marked `needs-triage`.
3. `needs-info` requests with reporter activity since the latest triage notes.

Show Engineering Plans awaiting review separately from unclassified Build
requests. Use their approval record and work kind, not a missing readiness
label, to interpret them. Let the maintainer select the work to examine.

## Triage a request

1. **Gather context.** Read the full issue and comments, dates, author, labels,
   and relationships. Read prior triage notes. Search code by domain concept
   for an existing implementation and report where you looked. Search Linear
   for overlapping requests and read prior rejection records using domain.md.
   Distinguish a duplicate request, implemented behavior, temporary deferral,
   and a rejected enhancement.
2. **Recommend.** Explain the proposed category and role, the relevant code
   findings, and any scope overlap. Wait for the maintainer's direction.
3. **Verify.** For a bug, try the reported steps in an appropriate development
   environment. Report confirmed behavior, a failed reproduction, or missing
   information. Verification does not authorize a production repair.
4. **Grill if needed.** Follow [finite-grill](../finite-grill/SKILL.md) when
   decisions are missing. Read and follow that file with the available agent;
   no particular skill-invocation tool is required. Resolve terms and decisions
   using domain.md and retain prior answers.
5. **Apply the outcome.** Use the configured mapping. For ready work, update
   the issue's current brief and post a short triage result. For `needs-info`,
   post the established facts and specific unanswered questions. For
   `needs-triage`, retain useful partial findings. For `wontfix`, record the
   reason and cancel: already-implemented work links to its implementation;
   rejected enhancements also update the relevant Linear decision record.
   Use the native duplicate relationship for confirmed duplicate requests.

Read back the result. Keep the issue body as the current contract and comments
as discussion and evidence. If the approved brief conflicts with the existing
body, reconcile the affected text; do not leave a competing specification in a
comment. Changes that exceed the approval stay proposed.

## Quick override

If the maintainer requests a role directly, trust their direction and skip the
grill. State the intended role, comment, or closure changes, then act within
the configured approval rules. If ready work lacks a brief, ask whether they
want one. A role change does not record another reviewer's approval.

## Brief template

Use behavior, interfaces, and concrete acceptance criteria that remain useful
after code moves. Avoid file paths and line numbers in the durable brief.
Link the governing specification and keep its scope intact. For
`ready-for-human`, state the judgment, access, or manual work that requires a
human. Use this template in the current issue body when it needs a brief:

```markdown
## Agent Brief

**Category:** bug / enhancement
**Summary:** The requested result.
**Specification:** Governing plan, if one exists.

**Current behavior:** What happens now and what was verified.
**Desired behavior:** What must happen, including relevant edge cases.

**Key interfaces:**
- Named contracts or types affected by the change.

**Acceptance criteria:**
- [ ] A specific, testable result.

**Out of scope:**
- An adjacent behavior this issue does not change.
```

## Needs-info template

```markdown
## Triage Notes

**What we have established:**
- Resolved fact or decision.

**What we still need from the reporter:**
- Specific question.
```

On resumption, read the prior notes and subsequent replies before recommending
the next role. Reuse settled answers instead of restarting the interview.
